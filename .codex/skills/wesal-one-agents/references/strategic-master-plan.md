## 0. فلسفة الخطة — كيف نضمن النجاح فعلياً

أربعة مبادئ تحكم كل شيء:

1. **بوابات، لا تواريخ.** كل مرحلة لها "بوابة خروج" بمعايير قياس واضحة. ما ننتقل للتالية إلا والبوابة مقفولة. التواريخ تقديرية؛ البوابات إلزامية.
2. **لا نبني فوق غير مؤكَّد.** كل مرحلة تبدأ بفحص read-only وتنتهي بمراجعة النتيجة المنشورة بالمتصفح.
3. **الإطلاق متدرّج، مو انفجار واحد.** طيار مغلق (ربط يدوي) → طيار مدفوع → إطلاق عام. كل خطوة تكشف المشاكل وهي صغيرة ورخيصة.
4. **برايد = العميل صفر.** متجرك هو ساحة الإثبات — أي ميزة لازم تشتغل لبرايد قبل ما تُباع لغيرك.

**القرار الأذكى في الخطة:** ما ننتظر اكتمال الأتمتة (Embedded Signup) عشان نبدأ نبيع. أول 3-5 تجار نربطهم **يدوياً** — زي ما ربطنا برايد — نتعلم منهم ونقبض منهم، والأتمتة تُبنى بالتوازي. هذا يقدّم أول إيراد أسابيع كاملة.

## 1. الصورة الكبيرة — ثلاثة مسارات

| المسار | الحالة | يحجب إيش؟ |
|---|---|---|

## المرحلة A — إغلاق التصميم (نظام المساحات)

**الهدف:** التطبيق يبان منتج محترم — كثيف، متّسق، ما "يتنفس هواء".

**المهام:**
1. فحص git ثم فحص read-only لنظام التباعد الحالي (الأمر جاهز في ملف النقل).
2. تعريف توكنات تباعد مركزية (قيم قليلة موحّدة: هوامش صفحة، padding بطاقة، ارتفاع ترويسة، تباعد أقسام).
3. التطبيق شاشة-شاشة: لوحة التحكم (مربعات نمط جيب/فلوسك) → الوارد → الإعدادات → البقية.
4. مراجعة بصرية جوال + لابتوب بعد كل نشر.

**بوابة الخروج:** كل الشاشات الرئيسية على التوكنات الموحّدة؛ لا قيم متناثرة جديدة؛ سطح المكتب لم يُمس.
**تقدير:** 4-7 أيام.

---

## المرحلة B — تصليب الأساس

**الهدف:** ما نبني فوق أرضية فيها شقوق.

**المهام:**
1. حسم الثغرات المفتوحة: #26 (زر "دفعة": تفعيل أو حذف — قرار)، #19 (meta_app_id للصفوف القديمة)، ITEM 5 (اقتطاع رد الوكيل — فحص AI_MAX_OUTPUT_TOKENS في Cloud Run).
2. **نسخ احتياطي:** التحقق أن Cloud SQL automated backups مفعّلة + **تجربة استرجاع فعلية مرة واحدة**. فقدان بيانات تاجر = نهاية الثقة بالمنصة.
3. مراقبة بسيطة: فحص uptime على الرابط + رؤية واضحة لأخطاء webhook.
4. مراجعة أسرار: كل التوكنات في Secret Manager / env — لا شيء في الكود أو السجلات.

**بوابة الخروج:** صفر ثغرات حرجة؛ استرجاع نسخة مجرَّب فعلياً؛ تنبيه يوصلك لو المنصة وقعت.
**تقدير:** 3-5 أيام.

## المرحلة C — البنية متعددة العملاء (أثقل مرحلة هندسياً)

**الهدف:** المنصة تخدم تاجراً ثانياً وثالثاً بعزل تام عن برايد.

**المهام بالترتيب:**
1. **Token resolver لكل عميل** (Secret Manager) — بدل الرجوع لتوكنات البيئة العامة.
2. **تسجيل/اشتراك webhook لكل عميل** (WABA/رقم/صفحة على التطبيق).
3. **فحص عزل البيانات** (read-only): تأكيد أن كل الاستعلامات مقيّدة بالـworkspace — ما يشوف تاجر محادثات تاجر ثاني.
4. **Embedded Signup** (JS SDK + config_id + تدفق النافذة) — آخر بند، لأن الطيار يدوي وما يحتاجه.

**بوابة الخروج:** تاجر تجريبي ثاني يُربط يدوياً، يستقبل ويرد، بعزل كامل عن برايد، بتوكناته الخاصة.
**تقدير:** 7-14 يوم (بدون Embedded Signup الذي يُبنى أثناء الطيار).

## المرحلة D — ميتا (متوازية مع كل ما سبق)

**الهدف:** الصلاحيات معتمدة والترحيل جاهز.

**المهام:**
1. **أول مهمة — اليوم:** التحقق من حالة المراجعة. مرّ ~3 أسابيع على التقديم — هل وصلت ردود/رفض/طلبات من ميتا؟
2. حسم وضع الصلاحيات (الأصل صلاحيتان، التقديم 12-13) حسب رد ميتا الفعلي — لو رُفض الموسّع، نعيد التقديم بالمسار النظيف (whatsapp_business_messaging + management فقط) ونوسّع لاحقاً.
3. حل مشكلة Test Number/WABA إن كانت لا تزال قائمة.
4. تسجيل screencasts إن طلبتها ميتا.
5. تفعيل "Login with JavaScript SDK" (#18) — مطلوب للتسجيل المضمن.

**بوابة الخروج:** صلاحيتا واتساب الأساسيتان معتمدتان كحد أدنى.
**تقدير:** عمل فعلي 2-4 أيام؛ الباقي انتظار ميتا (خارج سيطرتنا — لهذا المسار متوازي لا متسلسل).

## المرحلة E — الترحيل للإنتاج

**الهدف:** المنصة على هويتها النهائية.

**المهام:**
1. الترحيل من تطبيق التطوير (956632443920182) إلى تطبيق Wesal One (1437258534807702) — **فقط بعد اعتماد المراجعة**.

**بوابة الخروج:** تاجر يفتح الدومين، يسجّل دخول، والقنوات شغّالة على تطبيق الإنتاج.

## المرحلة F — التسعير والتفعيل

**الهدف:** فلوس تدخل بطريقة منظمة من أول يوم طيار.

**المهام:**
1. تسعير الطيار: سعر تأسيسي مخفّض "مدى الحياة" لأول 5 تجار — يكافئ مخاطرتهم المبكرة ويسهّل الإقناع. الأرقام قرارك — أنت التاجر.
2. الدفع: يدوي موثّق (حوالة / USDT — البنية مجرَّبة من برايد) + إيصال وسجل.
3. Onboarding: مستند ترحيب عربي بسيط + جلسة إعداد معك مباشرة لكل تاجر.

**بوابة الخروج:** أول تاجر يدفع ويتفعّل خلال يوم واحد من موافقته.
**تقدير:** 3-5 أيام (متداخلة مع G).

## المرحلة G — الطيار المغلق (الاختبار الحقيقي)

**الهدف:** 3-5 تجار حقيقيين يستخدمون المنصة يومياً وأنت شايف كل شيء.

**المهام:**
1. اختيار التجار من معارفك: يثقون فيك + نشاطهم فعلاً على واتساب + مستعدين يدفعون ولو رمزياً (اللي يدفع يستخدم؛ المجاني يُهمَل).
2. ربط يدوي لكل واحد + متابعة أسبوعية ثابتة.
3. قناة دعم واحدة: قروب واتساب معك.
4. سجل ملاحظات: كل شكوى/طلب يُسجَّل ويُصنَّف (حرج / مهم / لاحقاً).
5. دورة إصلاح أسبوعية بنفس منهجية Codex — وبناء Embedded Signup خلال هذي الفترة.

**بوابة الخروج:** أسبوعان متتاليان بدون عطل حرج + التجار يجدّدون عن قناعة + برايد نفسه شغّال على المنصة كعميل.
**تقدير:** ~3 أسابيع تشغيل.

## المرحلة H — الإطلاق العام

**الشروط (كلها، بدون استثناء):**
- بوابة G مقفولة.
- Embedded Signup شغّال: تاجر غريب يربط واتسابه **بدون تدخلك**.
- صفحة هبوط + تسعير نهائية على الدومين.
- قصة نجاح موثّقة بالأرقام (برايد: المبيعات من 2-3 إلى 5-8 يومياً).

**أسلوب الإطلاق:** هادئ ومتدرّج — قروبات التجار، معارفك، ثم توسّع. مو إعلان ضخم يجيب 100 تاجر على نظام عمره أسبوعين.

## 2. نظام الجودة (يسري على كل مرحلة — غير قابل للتفاوض)

1. فحص read-only قبل أي بناء.
2. أمر Codex دقيق (ROLE / TARGET / CONTEXT / TASK / CONSTRAINTS / OUTPUT).
3. typecheck + build:prod ينجحان قبل أي commit.
4. staging صريح للملفات — لا `git add -A` أبداً.
5. مراجعة تقرير Codex، ثم مراجعة النتيجة المنشورة بالمتصفح قبل اعتبار المهمة منجزة.
6. **المحميات (لا تُكسر):** الوارد الشغّال، بث SSE (`/api/inbox/stream` network-only)، توقيع webhook (HMAC SHA-256)، تخطيط سطح المكتب `lg+`، تطبيق Wesal One قيد المراجعة لا يُلمس.
