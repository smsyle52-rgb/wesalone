## القسم 0 — الحلقة التشغيلية (كيف تعمل عند «اتبع المهارة»)

1. اقرأ هذا الملف كاملاً + `WESAL_ONE_CHAT_HANDOFF.md` (الحالة الحيّة).
2. في جدول النطاقات (القسم 3)، جِد **أول نطاق حالته ليست ✅** — هذا نطاقك النشط. **نطاق واحد فقط في كل مرة.** لا تقفز.
3. حدّد حالته:
   - **⬜ لم يُفحص** → نفّذ **الفحص** (read-only): امسح الكود وقاعدة البيانات لما يخص النطاق. الفحص يغطّي **بُعدين معاً**:
     - **الأمان**: ثغرات مرتّبة بالخطورة (حرجة/عالية/متوسطة) — كل ثغرة: الخطر، الملف/السطر، كيف نتأكد، كيف يصلحها خبير.
     - **جودة التشغيل** (مثل مراجعة مهندس بشري): هل المنطق معمّم وكامل أم ناقص/مربوط؟ معالجة الأخطاء والحالات الحدّية؟ الأداء تحت الحمل (استعلامات N+1، فهارس، كاش)؟ نظافة الكود وقابلية الصيانة (تكرار، تعقيد)؟ تجربة التاجر سلسة؟ وجود اختبارات؟
     أنتج تقريراً يجمع الاثنين. **توقّف وانتظر القرار.** لا تعدّل.
   - **🔧 موثّقة الثغرات** → بعد موافقة المالك على القرارات، نفّذ **الإصلاح** خطوة-خطوة (نطاق ضيّق فقط). بعد كل تعديل: typecheck + build:prod. **توقّف وانتظر.**
   - **🔍 قيد التحقق** → اختبر مقابل **بوابة الإغلاق** للنطاق. لو نجحت، علّم ✅ واطلب من المالك تحديث الـhandoff.
4. لا commit ولا push أبداً — المالك يدفع بيده.
5. عند أي خطأ، اتبع **بروتوكول إصلاح الأخطاء** (القسم 2).

> القاعدة: لا تبدأ نطاقاً وبوابة سابقه مفتوحة. ميتا (App Review/قنوات) تتقدّم بالتوازي حصراً.

## القسم 1 — هدف المشروع والصورة الكاملة

**ما هو وصال ون:** منصّة B2B تعطي التاجر العربي **وكيل مبيعات ذكياً** يردّ على عملائه ويُنجز
مهمات (طلبات، متابعات، تصعيد) عبر قنوات ميتا. ليست "صندوق وارد" بل "موظف مبيعات يُباع للتجار".
الإثبات الحيّ: بوت برايد (متجر المالك) — رفع المبيعات اليومية وأدار مئات المحادثات بلا تدخل.

**القنوات الثلاث والصلاحيات المعتمدة:**
- **واتساب** — whatsapp_business_messaging + whatsapp_business_management (إرسال/استقبال + إدارة WABA). شغّال.
- **ماسنجر/صفحات فيسبوك** — pages_messaging + pages_manage_metadata + pages_show_list + pages_read_engagement + business_management.
- **إنستغرام** — instagram_basic + instagram_manage_messages (DM).
- **مزوّد تقني (Tech Provider).** App ID: 1437258534807702 (قيد المراجعة، لا يُلمس إلا بطلب صريح).

**تبعية حرجة:** لا توجد `catalog_management` ولا `ads_management` في الصلاحيات الحالية —
فأي ميزة تعتمد على الكتالوج/الإعلانات (مثل `send_product_media` أو مرآة الكتالوج) **تتطلّب التأكد من
الصلاحية قبل البناء**. لا نبني على صلاحية غير موجودة.

**نموذج العميل (Multi-tenant):** نموذج تجمّع (Pool) — بنية مشتركة وعزل منطقي بعمود
`workspace_id`. **العزل = أخطر نطاق:** أي تسرّب بين عميلين كارثة ثقة.

**الطبقات التقنية:** monorepo pnpm، Node 22، React 19 + Vite، Express 5، Drizzle ORM،
PostgreSQL (Cloud SQL)، GCP Cloud Run. النشر: Cloud Build trigger على push إلى `main`
(triggerان: api-server + worker). الـAI: Vertex AI / Gemini.

**الحالة الحالية:** المرحلة 1 (حلقة الرد) **مقفلة** ✅ — الـworker يـpoll، domain_events تُعالَج،
الـwebhook يستقبل (POST 200)، الـ401 محلول. التالي: هذه الخطة، بدءاً بالنطاق 1.

### ما أُنجز حتى الآن (ربط خطتَي الوكلاء والتنفيذية بهذه الخطة)
هذه الخطة (جاهزية الإطلاق) هي **الفهرس التشغيلي الموحّد** الذي يقود الملفين المرجعيين. ما تحقّق منهما:
- **حلقة الرد التلقائي** (خطة الوكلاء، المرحلة 1) ✅ — الـworker يستدعي الوكيل عند message.received، يُرسل لميتا، domain_events تُعالَج. → يقابل النطاق 6 (مقفل جزئياً).
- **التسجيل المضمن** (خطة الوكلاء، القسم 3 / المرحلة 5) — الواجهة والـbackend مبنيان: JS SDK، config_id، تبادل الكود، اشتراك التطبيق، تخزين توكن العميل **مشفّراً AES-256-GCM** في credentialsSecretRef. ⚠️ الناقص: **الاسترجاع وقت الإرسال غير مُفعّل** (التوكن لا يُقرأ/يُفك) → يُكمَّل في النطاق 5 (Token Resolver، المرحلة 4). → يقابل النطاقات 4 و5 و10.
- **نقل الدومين** wesal.one (المرحلة 7) ✅ — شغّال على Cloud Run.
- **الموثوقية**: الـworker له Cloud Build trigger، كل push ينشر api + worker تلقائياً ✅. → النطاق 6.
- **غير المبني بعد** (من خطة الوكلاء): المرحلة 2 (أدوات المهمات) والمرحلة 3 (جودة الاسترجاع/embeddings) → النطاق 5. مراحل A–H (الخطة التنفيذية) موزّعة على النطاقات 7–13.

> الخلاصة: الأساس (الرد + الربط + التخزين المشفّر + النشر) مبنيّ ومُختبَر. باقي العمل = **تصليبات أمنية + استرجاع التوكن لكل عميل + تعميم القنوات + جودة التشغيل + الاختبار + الإطلاق** — موزّع نطاقاً نطاقاً أدناه.

## القسم 2 — معايير الهندسة (كيف يُكتب الكود ويُصلَّح الخطأ)

### المحميات (لا تُكسر — تسري على كل نطاق)
1. الوارد الشغّال واستقبال برايد لا ينقطع ولو دقيقة.
2. بث SSE `/api/inbox/stream` يبقى network-only؛ الـService Worker لا يلمس `/api/*`.
3. توقيع webhook (HMAC SHA-256) لا يُضعَّف ولا يُتجاوَز في الإنتاج حتى لو غاب المتغير.
4. تخطيط سطح المكتب `lg+` لا يُمس في أي تعديل واجهة.
5. عزل الـworkspace في كل استعلام جديد — بلا استثناء.
6. لا ربط/فصل قنوات برمجياً دون طلب صريح من المالك.
7. أسرار/توكنات: Secret Manager/env فقط — لا تظهر في كود أو سجلات أو تقارير.
8. تطبيق Wesal One (1437258534807702) قيد المراجعة لا يُلمس إلا بطلب صريح.
9. staging صريح للملفات — لا `git add -A` أبداً؛ commit/push بيد المالك فقط.
10. **العميل لا يرى أي تعقيد تقني أبداً.** ممنوع تماماً أن يصل لعميل التاجر أي ذكر لموديل (Gemini/Vertex/AI/mock)، أو كلمة «مسودة/وضع تجريبي/draft»، أو رسالة خطأ تقنية أو stack. إذا تعذّر إنتاج رد حقيقي (فشل/غياب النموذج) → **الوكيل يسكت ويصعّد للبشر بصمت، ولا يرسل أي نص بديل**. التاجر يُشعَر؛ العميل لا يشوف شيئاً.

### مسار الأعطال الحيّة (Hotfix Lane)
أي ثغرة **تكسر التشغيل الحاضر** (مثل رد تقني يصل للعميل، أو موت وارد، أو رد مكرر) تُصلَّح **فوراً خارج الدور** بأمر إصلاح مستقل — لا تنتظر اكتمال فحص بقية النطاقات. الفحص للوضوح؛ الـhotfix لوقف النزيف. تُوثّق الثغرة وإصلاحها في نطاقها بعد الإصلاح.

### حاجز الإصلاح الآمن (إلزامي قبل أي تعديل كود)
المالك غير مبرمج؛ لذلك أي جلسة إصلاح تلتزم **بروتوكول إصلاح الأخطاء** (أعد الإنتاج → اعزل السبب → أصغر تعديل → تحقّق typecheck+build) **وتُرفق دائماً**:
- شرحاً بلغة بسيطة لِما سيتغيّر ولماذا (بلا مصطلحات غامضة).
- **خطة تراجع صريحة**: كيف يُعكَس التعديل لو خرب شيئاً (الملفات/الأسطر بالضبط).
- ما الذي يجب أن يختبره المالك يدوياً للتأكد أن العطل زال ولم ينكسر غيره.
لا إصلاح أكثر من عطل واحد في الجلسة. عند الشك، توقّف واسأل بدل التخمين.

### اصطلاحات الكود
- لا تعيد اختراع ما هو موجود — استخرج وأعد الاستخدام (مصدر حقيقة واحد لكل منطق).
- كل استعلام DB عبر Drizzle مقيّد بـ `workspace_id`؛ تجنّب الاستعلامات الخام غير المعلَّمة.
- كل endpoint يتحقق من مدخلاته (zod أو ما يماثله) قبل أي منطق.
- اتبع نمط الملفات الموجود (routes/services/workers)؛ لا تنثر منطقاً مكرّراً.
- TypeScript صارم؛ لا `any` بلا ضرورة موثّقة.

### بروتوكول إصلاح الأخطاء (التزم به عند أي عطل)
1. **أعد الإنتاج**: ثبّت كيف يظهر الخطأ بالضبط (لوق/خطوات).
2. **اعزل السبب الجذري** قبل أي تعديل — لا تخمّن وتعدّل.
3. **أصغر إصلاح ممكن**: عالِج السبب فقط، بلا توسّع في النطاق.
4. **تحقّق**: typecheck + build:prod، ثم اختبار يدوي للحالة التي فشلت.
5. **لا تصلح أكثر من شيء في نفس الجلسة** — كل عطل على حدة.

### النشر والتحقق
- كل push على `main` ينشر api-server + worker تلقائياً (~3–4 دقائق). تجنّب إعادة النشر اليدوي المتكرر (يطفّي النسخة الحيّة).
- بعد النشر، تحقّق من اللوق أن الـworker يـpoll والـwebhook يستقبل قبل اعتبار المهمة منجزة.

### صيغة الأوامر
عند توليد أي أمر تنفيذ: **ROLE / TARGET / CONTEXT / TASK / CONSTRAINTS / OUTPUT**.

## القسم 3 — تسلسل النطاقات وجدول الجاهزية (الترتيب ملزم)

> رموز الحالة: ⬜ لم يُفحص · 🔍 قيد الفحص · 🔧 قيد الإصلاح · ✅ مقفل
> **كل نطاق يُفحص ببُعدين: الأمان + جودة التشغيل** (أداء، معالجة أخطاء، نظافة كود، تجربة، اختبار) — مثل مراجعة مهندس بشري، لا ثغرات فقط.
> تُحدَّث حالة كل نطاق وثغراته وقراراته هنا بعد كل جولة (هذا هو السجلّ الحيّ للهندسة).

### النطاق 1 — المصادقة والجلسات · الحالة: 🔍 (مفحوص، الثغرات موثّقة)
**ما يُفحص:** آلية تسجيل الدخول (جلسة/JWT/OAuth)؛ أين تُخزّن الجلسة ومدتها وتجديدها؛
أعلام الكوكي (httpOnly/secure/sameSite)؛ `SESSION_SECRET` من Secret Manager وقوّته؛
هل تسجيل الخروج يُبطل الجلسة فعلاً؛ rate limit على مسارات المصادقة؛ تجزئة كلمات المرور إن وُجدت (bcrypt/argon2) وعدم تسجيلها.
**الخريطة المعمارية:** دخول POST /api/auth/login → bcrypt.compare → req.session.user؛ جلسة express-session + connect-pg-simple (جدول session في Postgres)، كوكي khadamatak.sid (httpOnly، secure بالإنتاج، sameSite lax)؛ middleware requireSession؛ /internal/* محمية بـ INTERNAL_SECRET (timingSafeEqual).
**الثغرات المكتشفة (فُحص 15 يونيو 2026):**
- عالية: H1 session fixation عند login/register بلا regenerate (auth.routes.ts:115,69) | H2 الجلسات لا تُبطل عند تغيير كلمة المرور (auth.routes.ts:319)
- متوسطة: M1 apiLimiter معطّل (routes/index.ts) | M2 CORS يقبل الكل لو ALLOWED_ORIGINS فارغ — fail-open (app.ts:44) | M3 resend-verification بلا rate limit (auth.routes.ts:185) | M6 switch-workspace استعلام العضوية بلا فلتر workspaceId (auth.routes.ts:359)
- منخفضة: L1 sameSite lax بدل strict | L3 INTERNAL_SECRET اختياري بـfallback فارغ (env.ts:41)
**القرارات:** الجيد مثبت ✅ bcrypt/12، هاش توكنات SHA-256، توكنات استعادة لمرة واحدة، rate limiters على auth. L1 يُختبر مع Facebook Login (النطاق 4). CSRF يُراجَع في النطاق 9. H1/H2/M-fail-open تُصلَّح ضمن تصليبات الأمان.
**بوابة الإغلاق:** لا توجد ثغرة مصادقة حرجة/عالية؛ الجلسات آمنة ومنتهية الصلاحية؛ الأسرار من Secret Manager.

### النطاق 2 — عزل العملاء (Tenant Isolation) · الحالة: 🔍 · ⚠️ الأخطر
**ما يُفحص:** هل **كل** استعلام DB مقيّد بـ `workspace_id`؛ هل يوجد middleware يفرض workspace
المستخدم الحالي؛ ثغرة IDOR (هل يصل مستخدم لمحادثة/طلب/دفعة عميل آخر بتغيير id)؛ هل القنوات الثلاث
معزولة بنفس الصرامة؛ تطبيق Row-Level Security في Postgres (مثالي)؛ سجلات التدقيق تحمل سياق العميل.
**الثغرات المكتشفة (فُحص 15 يونيو 2026):**
- العزل الأساسي متماسك ✅ على القنوات الثلاث (نمط assertContactOwned ممتاز)
- ضعف دفاع-متعدد-الطبقات (ليست ثغرات فعلية): M4 استعلامات الرسائل بلا workspaceId صريح (conversations.routes.ts:323,636) | M5 recalcTotal تجلب الطلب بلا workspaceId (orders.routes.ts:40) | M7 بعض UPDATE بلا workspaceId في الشرط (payments:530، conversations:391، orders:253)
- منخفضة: L2 لا Row-Level Security في Postgres
**القرارات:** العزل التطبيقي يكفي للإطلاق الأول. L2 (RLS) مؤجّل بوعي — مخاطرة مقبولة موثّقة، يُضاف قبل التوسّع. سطح حقن SQL يُسدّ في النطاق 9. M4/M5/M7 تُضاف كطبقة دفاع ثانية.
**بوابة الإغلاق:** استحالة وصول عميل لبيانات عميل آخر عبر أي مسار (API/قناة/تقرير)؛ كل استعلام مُثبت أنه مقيّد.

### النطاق 3 — الأسرار والاعتمادات · الحالة: 🔍
**ما يُفحص:** توكنات ميتا لكل عميل في Secret Manager (`credentialsSecretRef`) لا توكن مشترك مكشوف؛
مسح الكود لأي سر مكتوب نصاً (hardcoded) أو يظهر في اللوق؛ تاريخ git (هل سبق رفع سر → تدوير + تنظيف)؛
`INTERNAL_SECRET` يحمي `/internal/agent-reply` ويُتحقق منه صح.
**خريطة تدفّق التوكن:** الإرسال الحي (worker) يستخدم META_SYSTEM_USER_TOKEN — توكن مشترك واحد لكل العملاء؛ الخدمات (meta-graph، meta-catalog-sync) مشترك أيضاً؛ توكن العميل مخزّن مشفّراً AES-256-GCM (enc:v1:) في credentialsSecretRef لكن ⚠️ لا يُقرأ/يُفك وقت الإرسال (resolver not enabled)؛ الحقن عبر Cloud Build --set-secrets ← Secret Manager.
**الثغرات المكتشفة (فُحص 15 يونيو 2026):**
- عالية: H3-1 توكن مشترك واحد لكل العملاء، الاسترجاع لكل-عميل غير مُفعّل (outbox-worker/index.ts:138,171؛ meta-graph.ts:31؛ التخزين غير المستهلك integrations.routes.ts:767). **= المرحلة 4 (Token Resolver) بأكملها، تُنفّذ ضمن النطاق 5 — ليست إصلاح سطر.**
- متوسطة: M3-1 مفتاح تشفير التوكنات مشتقّ من SESSION_SECRET، يحتاج مفتاح مستقل META_TOKEN_ENC_KEY (integrations.routes.ts:126) | M3-2 .env خارج .gitignore (الصور آمنة عبر .dockerignore، التاريخ نظيف) | M3-3 INTERNAL_SECRET بـfallback فارغ، يُجعل requireEnv (env.ts:41، worker:8)
- منخفضة: L3-1 worker بلا redaction (لا يطبع توكنات) | L3-2 PIN تسجيل الرقم ثابت "000000" | L3-3 client_secret في query عند تبديل OAuth
**القرارات:** الجيد مثبت ✅ صفر أسرار في الكود/اللوق/تاريخ git، كله من Secret Manager، توكنات العملاء مشفّرة AES-256-GCM وقت التخزين، SESSION_SECRET مطلوب fail-fast، logger يُخفي auth/cookie، INTERNAL_SECRET timingSafeEqual fail-closed. H3-1 تُنفّذ ضمن النطاق 5/المرحلة 4. M3-1/M3-2/M3-3 تُجمع مع تصليبات النطاق 9.
**بوابة الإغلاق:** صفر أسرار في الكود/اللوق/التاريخ ✅ متحقّقة. "توكن لكل عميل في Secret Manager" ❌ معلّقة على Token Resolver (النطاق 5/المرحلة 4).

**القرارات:** الجيد مثبت ✅ CORS fail-closed بالإنتاج (M2 مُصلَح، app.ts:47)، apiLimiter مطبَّق + مجموعة محدّدات شاملة (auth/signup/ai/payment/report/password 8–300، sessionOrIp)، معالج أخطاء بلا تسريب stack (رسائل عربية + code، app.ts:105)، securityHeaders (nosniff/DENY/Referrer/Permissions)، trust proxy 1، عزل raw-body للـHMAC، zod مطبَّق بسعة، INTERNAL_SECRET+webhook timingSafeEqual fail-closed، الأسرار من Secret Manager (cloudbuild يحقن META_APP_SECRET/WEBHOOK_SECRET/VERIFY_TOKEN/SESSION/INTERNAL). الأولويات: M4-1 (محمية #1) + H4-1 (قبل أي mount للمعمّم) → S9-1 (throttle الويبهوك) → S9-2/S9-3 (HSTS+CSP) → M3-1 (مفتاح تشفير مستقل) → S9-5 (audit في CI) → S9-4 (تصغير حدّ JSON). **تصحيح:** أغلب أساسيات OWASP مُطبَّقة فعلاً (خلافاً لانطباع "نطاق غير مبدوء")؛ المتبقّي تشديدات محدّدة لا ثغرات حرجة.
