2. **دفاع في العمق (محمية #10):** غُلِّف حفظ الرسالة+الـoutbox بـtry/catch؛ عند أي فشل مستقبلي → تصعيد المحادثة لـ`human` + `notifyWorkspace` + إبلاغ الـworker بالتصعيد (الحدث `done` لا `failed`، فلا تتكرّر الحلقة الصامتة) — بدل إسقاط العميل بصمت.
3. **استرداد:** الأحداث الـ11 الفاشلة أُعيد ضبطها `pending` بعد النشر؛ منطق نافذة 24س (Q3) يرسل الطازج ويصعّد المنتهي للبشر.

**الدرس المستفاد (حاكم):** `messages.sender_id` FK لـ`users` فقط. أي رسالة من غير مستخدم بشري (وكيل/نظام/أتمتة) **يجب** أن تستخدم `senderId=null` + `senderName` وصفي، لا معرّف من جدول آخر. تحقّق من هذا في أي إدراج مستقبلي في `messages`.

#### تشريح PD-10 — النموذج لا يلتزم بصيغة الأدوات (المرحلة 1 مُصلَحة 18 يونيو 2026)
**العَرَض:** بعد إصلاح PD-8 وPD-9، ظلّ `create_order` متذبذباً: نفس الطلب ("كرتونين مياه بـ2000 ريال يمني") ينجح مرة (20:27 استدعى الأداة) ويفشل أخرى (21:13 لم يُنشئ طلباً رغم ردّ مهذّب "تلقينا طلبك").

**التشخيص (من `ai_messages.metadata`، بوليان نظيف):** للتشغيل الفاشل `has_raw=f` — أي `rawOutput` غير مخزّن، ويُخزَّن فقط حين `parsedOutput.reply !== aiOutput.content`. غيابه يعني أن مخرج النموذج **لا يحوي JSON إطلاقاً** → النموذج ردّ **نصّاً عربياً صرفاً** بلا `{reply, tool_calls}`. تشغيل آخر وضع `items`/`currency` في **جذر** JSON بلا لفّ `create_order`. ثلاثة سلوكيات مختلفة لنفس الطلب = عدم التزام بنيوي.

**الجذر المركّب:** (1) الاعتماد على JSON نصّي بلا `responseMimeType` ولا function calling — لا ضمان للبنية. (2) `draft_reply` خارج `JSON_TASK_TYPES`، فحتى شبكة الأمان الموجودة (نص بلا JSON → تراجع للmock → تصعيد صامت) **لا تعمل لردود الوكيل**؛ النص الصرف يمرّ بلا فحص.

**الإصلاح — المرحلة 1 (ai-provider.ts + agent-reply.ts):**
1. علَم `responseFormat: "json" | "text"` في `AiRunInput`؛ `agent-reply` يمرّر `"json"` **فقط عند تفعيل الأدوات** (`executableTools.length > 0`). بلا أدوات، الردّ نصّ حرّ كما هو.
2. مُساعد `wantsJson(input)` يوحّد ثلاثة: (أ) فرض `responseMimeType: "application/json"` في `generationConfig` لكلا المزوّدَين (Gemini SDK + Vertex REST)، (ب) خفض الحرارة لـ≤0.1، (ج) تفعيل شبكة أمان "نص بلا JSON → تصعيد صامت" لردود الوكيل أيضاً.
3. **الأثر:** يقضي على ردّ النص الصرف (21:13) **وعلى فئة PD-8** (JSON صالح = أحرف تحكّم مهرَّبة). الحالة المتبقّية (حقول في الجذر) أندر مع الـprompt الصريح، وتُحسَم نهائياً في المرحلة 2.

**المرحلة 2 (مؤجلة — قرار المالك):** الاستدعاء الأصلي للأدوات (function declarations + قراءة `functionCall` المنظّم) — يضمن البنية حسابياً ويقتل الفئة كلها. يلمس المزوّدَين + `agent-tools` + `agent-reply`؛ يحتاج اختباراً دقيقاً.

**الدرس المستفاد (حاكم):** استدعاء الأدوات عبر JSON نصّي غير موثوق لمسار حرج. افرض المخرج المنظّم (`responseMimeType`/function calling)، و**اربط فرض JSON بحالة "الأدوات مفعّلة" لا بنوع المهمة فقط** — وإلا تتسرّب ردود بلا بنية بلا شبكة أمان.

#### تشريح PD-9 — `create_order` يفشل دوماً عند ذكر العملة بالعربية (مُصلَح 17 يونيو 2026)
**العَرَض:** أثناء اختبار `create_order` حيّاً، وصل العميل رسالة "أحتاج أن أحوّل طلبك للفريق" في كل مرة — حتى بعد إصلاح PD-8. الملاحظة في DB: `Agent tool failed: create_order - invalid_enum_value: received 'ريال يمني', expected 'YER'|'SAR'|'USD'` في موضعَين (`currency` الجذر + `items[0].currency`).

**التشخيص:** النموذج يمرّر العملة كما ذكرها المستخدم ("ريال يمني") بدل رمز ISO. `createOrderSchema.parse()` يرمي `ZodError` → `hasToolProblem=true` → `finalReply` يُستبدل بجملة التحويل للفريق → لا طلب يُنشأ أبداً. مؤكّد بسجلّ DB + خطأ Zod الكامل. ملاحظة: الـprompt (`publicToolSpec`) لم يذكر الرموز المسموحة، فالنموذج لم يعلم.

**الإصلاح (agent-tools.ts — طبقتان):**
1. **`coerceCurrency()`:** تُطبّع النص العربي/الحر لرمز ISO قبل التحقّق (يمني→YER، سعودي→SAR، دولار→USD). تُطبَّق عبر `z.preprocess` على جميع حقول `currency` في `createOrderSchema` (الجذر + كل عنصر في `items`).
2. **`z.preprocess(Number)` للأرقام:** `quantity`, `unitPrice`, `discount` — تحوّل نصّاً أو null لرقم بدل رفض المدخل، مثل `z.coerce` لكن بتحكّم أوضح.
3. **الـprompt:** `publicToolSpec` الآن يذكر `currency (YER/SAR/USD, e.g. YER for ريال يمني)` صراحةً لتوجيه النموذج من المصدر.

**الدرس المستفاد:** مدخلات LLM للأدوات تأتي من لغة العميل الطبيعية — الـschema يجب أن **يطبّع لا يرفض** أي إدخال طبيعي متوقّع (عملات، وحدات، كميات نصية). `z.preprocess` هو النمط الصحيح لكل حقل قد يأتي بصيغة بديلة.

#### تشريح PD-8 — JSON خام يصل للعميل + استدعاءات أدوات ضائعة (مُصلَح 16 يونيو 2026)
**العَرَض:** أثناء اختبار أدوات المرحلة 2 حيّاً (المالك أرسل طلب "3 كراتين مياه بـ1200")، وصل العميل النصّ الخام `{"reply":"..."}` بأقواس JSON ظاهرة بدل النص النظيف. كذلك `create_order` لم يُستدعَ (`tool_results=[]`).

**التشخيص (إثبات محلي بالمُدخل الحقيقي):** عند تفعيل الأدوات، يُخرج النموذج JSON `{"reply":...,"tool_calls":[...]}`. لكنه يضع **أسطراً حقيقية** (`\n` غير مهرَّبة) داخل قيمة `reply` متعددة الفقرات → `JSON.parse` يرمي (السطر الحقيقي داخل سلسلة = JSON غير صالح) → `catch` كان يُرجع `fallback = content` الخام → العميل يرى `{"reply":...}`. **والأخطر:** نفس الفشل يُسقط `tool_calls` كاملاً، فأي ردّ متعدد الأسطر يحوي استدعاء أداة **لا تُنفَّذ أداته أبداً** — تفسير محتمل لعدم نزول الطلبات. الردود سطر-واحد كانت تنجح (لذلك بعضها ظهر سليماً وبعضها لا).

**الجذر:** `parseAgentToolResponse` (agent-tools.ts) هشّ أمام أحرف التحكّم داخل سلاسل JSON.

**الإصلاح (agent-tools.ts):** تحليل متين بثلاث طبقات: (1) `JSON.parse` مباشر، (2) عند الفشل: تهريب أحرف التحكّم **داخل السلاسل فقط** (لا تُلمَس بنية الكائن) ثم إعادة التحليل، (3) آخر خط دفاع: استخراج `reply` بـregex فلا يصل العميل JSON خاماً أبداً. **مُثبَت** باختبار محلي على المُدخل الفاشل الحقيقي: النص يُستخرج نظيفاً + `tool_calls` تُستخرج صحيحاً + السطر-الواحد بلا انحدار.

**الدرس المستفاد (حاكم):** أي محلّل JSON لمخرجات نموذج لغوي **يجب** أن يكون متيناً أمام أحرف التحكّم غير المهرَّبة والـpretty-printing — النماذج لا تضمن JSON صالحاً. لا تثق بـ`JSON.parse` المباشر على مخرجات LLM، وامنع دوماً وصول JSON خام للعميل (محمية #10).

### حاجز الإصلاح الآمن (إلزامي قبل أي تعديل كود)
المالك غير مبرمج؛ لذلك أي جلسة إصلاح تلتزم **بروتوكول إصلاح الأخطاء** (أعد الإنتاج → اعزل السبب → أصغر تعديل → تحقّق typecheck+build) **وتُرفق دائماً**:
- شرحاً بلغة بسيطة لِما سيتغيّر ولماذا (بلا مصطلحات غامضة).
- **خطة تراجع صريحة**: كيف يُعكَس التعديل لو خرب شيئاً (الملفات/الأسطر بالضبط).
- ما الذي يجب أن يختبره المالك يدوياً للتأكد أن العطل زال ولم ينكسر غيره.
لا إصلاح أكثر من عطل واحد في الجلسة. عند الشك، توقّف واسأل بدل التخمين.

### اصطلاحات الكود
- لا تعيد اختراع ما هو موجود — استخرج وأعد الاستخدام (مصدر حقيقة واحد لكل منطق).
- كل استعلام DB عبر Drizzle مقيّد بـ `workspace_id`؛ تجنّب الاستعلامات الخام غير المعلَّمة.
- كل endpoint يتحقق من مدخلاته (zod أو ما يماثله) قبل أي منطق.
- اتبع نمط الملفات الموجود (routes/services/workers)؛ لا تنثر منطقاً مكرّراً.
- TypeScript صارم؛ لا `any` بلا ضرورة موثّقة.

### بروتوكول إصلاح الأخطاء (التزم به عند أي عطل)
1. **أعد الإنتاج**: ثبّت كيف يظهر الخطأ بالضبط (لوق/خطوات).
2. **اعزل السبب الجذري** قبل أي تعديل — لا تخمّن وتعدّل.
3. **أصغر إصلاح ممكن**: عالِج السبب فقط، بلا توسّع في النطاق.
4. **تحقّق**: typecheck + build:prod، ثم اختبار يدوي للحالة التي فشلت.
5. **لا تصلح أكثر من شيء في نفس الجلسة** — كل عطل على حدة.

### النشر والتحقق
- كل push على `main` ينشر api-server + worker تلقائياً (~3–4 دقائق). تجنّب إعادة النشر اليدوي المتكرر (يطفّي النسخة الحيّة).
- بعد النشر، تحقّق من اللوق أن الـworker يـpoll والـwebhook يستقبل قبل اعتبار المهمة منجزة.

### صيغة الأوامر
عند توليد أي أمر تنفيذ: **ROLE / TARGET / CONTEXT / TASK / CONSTRAINTS / OUTPUT**.

## القسم 4 — ملاحظات حاكمة
- **الأعطال الإنتاجية المؤكّدة (PD-1…PD-6) قبل كل شيء.** «المنصّة تشغيلية على الآخر» = الهدف الحاكم؛ ما يعطّل تاجراً حيّاً يسبق أي نطاق نظري ⬜. الأمن/العزل يبقى مسبقاً لأي تعديل (لا يُكسر أثناء إصلاح عطل).
- **الأمن والعزل قبل الميزات.** نطاق 1→2→3 يسبق بناء أدوات المرحلة 2، لأن تسرّب عميل أخطر من ميزة ناقصة.
- **«مبنيّ-غير-موصول» نمط متكرر:** قبل بناء أي ميزة، تحقّق أنها ليست مبنيّةً يتيمة (worker/استقبال معمّم/outbox ثانٍ) — الوصل أرخص من إعادة البناء (النطاق 30).
- **تأكّد من الصلاحية قبل البناء** (خاصة الكتالوج/الإعلانات الغائبة، ومكالمات واتساب).
- **القنوات الثلاث** تُفحص معاً في كل نطاق ذي صلة — لا نفترض أن ما يصحّ لواتساب يصحّ لغيرها.
- **مرجع التفاصيل الهندسية:** خطة الوكلاء (`agents-master-plan.md`) للقرارات المقفلة 1–7؛ الخطة التنفيذية (`strategic-master-plan.md`) لخارطة الأعمال A–H. هذه الخطة (جاهزية الإطلاق) هي السجلّ التشغيلي الذي يقودهما.
