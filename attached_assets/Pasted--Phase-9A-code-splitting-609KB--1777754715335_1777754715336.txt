الآن ابدأ Phase 9B فقط:
Staging Deployment Execution / Deployment Runbook.

ممنوع:
- لا تضف features جديدة
- لا تضف code-splitting الآن
- لا تضف integrations
- لا تضف AI جديد
- لا تضف payment gateway
- لا تضف WhatsApp API
- لا تضف email provider
- لا تغيّر business logic
- لا تغيّر schema
- لا تستخدم production secrets
- لا تنشر على production

الهدف:
تجهيز وتنفيذ أو توثيق نشر staging بطريقة آمنة وقابلة للتكرار.

Scope:

1. تحقق من وضع النشر الحالي

افحص:
- هل API server production build يعمل من dist/index.mjs؟
- هل frontend build ينتج dist/public؟
- هل backend يخدم frontend static أم frontend يحتاج hosting منفصل؟
- هل staging المقترح سيكون:
  A) Cloud Run واحد يخدم API + static frontend
  B) Cloud Run للـ API + Cloud Storage/CDN للواجهة
  C) Replit deployment مؤقت
- لا تغيّر المعمارية إلا لو كان fix بسيطاً وضرورياً.

2. Production Start Validation

اختبر محلياً أو في البيئة الحالية:
- build API
- build frontend
- start production command إن موجود
- healthz
- readyz
- smoke test ضد السيرفر المنتج

إذا production start غير واضح:
- أضف script واضح مثل:
  - start
  - start:prod
بشرط ألا يكسر dev.

3. Static Frontend Decision

إذا backend لا يخدم static frontend:
- لا تبنِ حل كبير الآن.
- وثّق أن الواجهة تُستضاف منفصلة في staging.
- اكتب خيارين:
  - frontend على Cloud Storage/CDN
  - أو Cloud Run واحد لاحقاً مع static serving

إذا كان من السهل أن يخدم API ملفات dist/public بدون كسر:
- اقترح patch صغير فقط
- لا تنفذه إلا إذا كان آمناً وضرورياً.

4. Staging Deployment Runbook

أضف في replit.md أو ملف DEPLOYMENT_STAGING.md:

- إنشاء Cloud SQL staging
- تفعيل PITR إن أمكن
- إنشاء DB user
- إعداد DATABASE_URL
- إعداد SESSION_SECRET
- إعداد ALLOWED_ORIGINS
- إعداد GEMINI_API_KEY optional
- تشغيل migrations
- تشغيل Cloud Run أو Replit deployment
- healthz/readyz
- smoke tests
- rollback notes

5. Secrets Checklist

وثّق:
- أين توضع DATABASE_URL
- أين توضع SESSION_SECRET
- أين توضع GEMINI_API_KEY
- لا secrets في repo
- لا secrets في logs
- Secret Manager لاحقاً للإنتاج

6. Staging Smoke Test

تأكد أن scripts/staging-smoke-test.sh يدعم:
- BASE_URL
- email عشوائي للتسجيل
- password آمن للاختبار
- طباعة نتائج واضحة
- exit code غير صفر عند الفشل

إذا يحتاج تحسين صغير، نفذه.

7. CORS / Origins

راجع:
- ALLOWED_ORIGINS في staging
- هل frontend origin موثق؟
- لا wildcard في staging/production إذا credentials=true

8. Migration Verification

وثّق أو اختبر:
- db:migrate على DB فارغة يطبّق 0000 + 0001
- لا db:push في staging
- readyz بعد migration
- smoke test بعد migration

لا تشغّل migrate على أي production.

9. Tests Required

شغّل:
- pnpm run typecheck:libs
- pnpm --filter @workspace/api-server run typecheck
- pnpm --filter @workspace/web run typecheck
- pnpm --filter @workspace/api-server run build
- pnpm --filter @workspace/web run build

Health:
- GET /api/healthz
- GET /api/readyz

Smoke:
- bash scripts/staging-smoke-test.sh ضد البيئة الحالية أو BASE_URL محدد

Security:
- لا secrets hardcoded
- CORS موثق
- cookies secure في production
- no production keys in repo

بعد التنفيذ أعطني:
1. الملفات التي تغيرت
2. هل production start واضح أم يحتاج قرار hosting؟
3. هل backend يخدم frontend static أم لا؟
4. نتائج typecheck
5. نتائج build
6. نتائج healthz/readyz
7. نتائج smoke test
8. staging deployment runbook summary
9. secrets checklist

12. المخاطر المتبقية قبل staging الفعلي
