Payments Stabilization — المدفوعات وربطها بالطلبات.

- لا تضف Debts
- لا تضف Collection
- لا تضف AI
- لا تضف Gemini
- لا تضف Automation
- لا تضف Integrations
- لا تضف Payment Gateway خارجي

- لا تضف Bulk Updates

Phase 4A Scope:

1. الهدف

تثبيت المدفوعات اليدوية داخل المنصة:
- تسجيل دفعة مرتبطة بطلب و/أو عميل
- دعم الدفع الجزئي والكلي
- دعم طرق الدفع اليمنية
- دعم رقم الحوالة
- دعم حالة pending/confirmed/rejected
- تحديث paid_amount في الطلب عند تأكيد الدفعة فقط
- عرض remaining_amount للطلب
- Audit logs
- Contact timeline
- منع AI أو أي تكامل خارجي من تأكيد الدفع

2. قواعد مطلقة

- كل payment يبدأ status=pending دائماً.
- لا يوجد payment provider خارجي.
- لا توجد API حقيقية لكريمي أو جوالي.
- Kuraimi/Jawali/manual methods فقط كطرق يدوية.
- confirm/reject فقط لـ owner/manager/accountant.
- reject يتطلب reject_reason غير فارغ بعد trim.
- confirmed/rejected terminal.
- لا يمكن تأكيد أو رفض دفعة ليست pending.
- لا يمكن تعديل amount/currency/method بعد confirm/reject.
- AI ممنوع من confirm/reject/payment state.
- لا debts في هذه المرحلة.

4. Exchange Rate Snapshot

عند إنشاء payment:
- إذا currency = YER:
  base_amount_yer = amount
  exchange_rate_snapshot = null أو {rate:1}
- إذا currency = SAR أو USD:
  استخدم آخر exchange_rate فعال داخل نفس workspace.
  احفظ:
  exchange_rate_id
  exchange_rate_snapshot
  base_amount_yer = amount * rate

إذا لا يوجد سعر صرف لعملة غير YER:
- أرجع 400:
  "يجب إدخال سعر الصرف قبل تسجيل دفعة بهذه العملة"

لا تعيد حساب المدفوعات القديمة عند تغير سعر الصرف.

5. Order Payment Logic

عند إنشاء payment:
- status=pending
- لا تغيّر order.paid_amount

عند confirm payment:
- إذا order_id موجود:
  - زد order.paid_amount بمبلغ الدفعة بعملة الطلب أو ما يعادلها حسب القواعد
  - احسب remaining_amount للعرض
- إذا amount المؤكد يجعل paid_amount يتجاوز total_amount:
  أرجع 422:
  "مبلغ الدفعة يتجاوز المبلغ المتبقي للطلب"

عند reject:
- لا تغيّر order.paid_amount

ملاحظة:
إذا order.currency مختلفة عن payment.currency:
- استخدم base_amount_yer للمقارنة إذا كان order بالـ YER
- أو أرجع 400 حالياً:
  "عملة الدفعة يجب أن تطابق عملة الطلب في هذه المرحلة"
اختر الخيار الأبسط والأكثر أماناً واذكره في التقرير.

6. Backend APIs

Payments:
- GET /api/payments
- POST /api/payments
- GET /api/payments/:id
- PATCH /api/payments/:id
- POST /api/payments/:id/confirm
- POST /api/payments/:id/reject

Payment Methods:
- GET /api/payment-methods
- POST /api/payment-methods
- PATCH /api/payment-methods/:id
- DELETE أو deactivate /api/payment-methods/:id

Exchange Rates:
- GET /api/exchange-rates
- POST /api/exchange-rates
- PATCH /api/exchange-rates/:id

كل API يجب أن:
- يستخدم requireSession
- يستخدم requirePermission المناسب
- يكون workspace-scoped
- لا يقبل workspace_id من body/query
- يرجع رسائل عربية
- يسجل audit log للكتابة
- يضيف contact_timeline event عند وجود contact_id

7. Permissions

استخدم:
- payments:read
- payments:create
- payments:update إن وجد، فقط لتعديل pending
- payments:confirm
- payments:reject
- payments:export إن وجد
- settings:manage أو payments:manage_methods لطرق الدفع
- exchange_rates:read و exchange_rates:manage إن وجدت، أو settings:manage مؤقتاً

أدوار:
- owner/manager: كل شيء
- accountant: read/create/confirm/reject وإدارة exchange rates إن كان مناسباً
- agent: create فقط أو حسب seed الحالي، بدون confirm/reject
- viewer: read فقط
- no one except owner/manager/accountant confirms payments

10. State Machine

Payments:
- pending → confirmed
- pending → rejected
- confirmed terminal
- rejected terminal

اختبارات:
- confirmed → rejected يفشل
- rejected → confirmed يفشل
- pending → confirmed ينجح
- pending → rejected بدون reason يفشل
- pending → rejected مع reason ينجح

11. اختبارات إلزامية

Typecheck:
- pnpm --filter @workspace/api-server run typecheck
- pnpm --filter @workspace/web run typecheck
- pnpm run typecheck:libs إن لزم

RBAC:
- viewer GET /api/payments → 200
- viewer POST /api/payments → 403
- agent POST /api/payments → 201 إذا seed يسمح
- agent POST /api/payments/:id/confirm → 403
- accountant POST /api/payments/:id/confirm → 200
- accountant POST /api/payments/:id/reject → 200
- viewer POST /api/payments/:id/reject → 403

Workspace isolation:
- POST payment مع workspace_id مختلف في body → يتجاهله
- payment على order من workspace آخر → 404 أو 403
- payment على contact من workspace آخر → 404 أو 403
- confirm payment من workspace آخر → 404 أو 403

Payment safety:
- إنشاء payment يجعل status=pending
- pending payment لا يغيّر order.paid_amount
- confirm payment يحدّث order.paid_amount
- reject payment لا يغيّر order.paid_amount
- reject بدون reason أو reason مسافات فقط → 400
- confirm payment أكبر من المتبقي → 422
- confirm/reject payment غير pending → 400 أو 422

Exchange rates:
- YER payment يعمل بدون exchange rate
- USD/SAR payment بدون exchange rate → 400
- USD/SAR payment مع exchange rate → base_amount_yer صحيح
- تغيير exchange rate لاحقاً لا يغيّر payment snapshot

Order payment status:
- order بدون دفعات confirmed → unpaid
- دفعة جزئية confirmed → partial
- دفعات confirmed تساوي total_amount → paid

Audit/Timeline:
- payment create audit + timeline
- payment confirm audit severity critical + timeline
- payment reject audit severity critical + timeline
- exchange rate create audit

UI:
- PaymentsPage RTL
- reject modal لا يسمح بسبب فارغ
- أزرار confirm/reject تظهر حسب الصلاحية
- OrdersPage يعرض paid/remaining
- زر تسجيل دفعة في order يعمل
- لا يوجد debt UI
- لا يوجد payment gateway UI
- لا نصوص إنجليزية للمستخدم
