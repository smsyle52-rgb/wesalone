# تدقيق نظام التجارة: المخزون والطلبات والمدفوعات

## النطاق

تم التدقيق من `main` عند commit `b59b0487f411b5b76d18cf710c20e72f2e6184cd`. هذا الفرع لا يغيّر ملفات واتساب أو التسجيل المضمّن أو القوالب، ولا يعتمد على Medusa أو Vendure كتطبيقات.

## الموجود الجيد الذي سيبقى

- الطلب مرتبط بـ `workspaceId` ويدعم `contactId` و`conversationId` و`assignedMembershipId`.
- توجد واجهة طلبات حالية وسجل تدقيق وDomain Events.
- جميع استعلامات المنتجات والطلبات والمدفوعات الحالية تقيد البيانات بمساحة العمل المشتقة من جلسة الخادم.
- المدفوعات سجلات مستقلة ويمكن ربطها بالطلب والعميل، مع قبول ورفض.

## الفجوات المؤكدة

1. `inventory_products.quantity_available` كمية واحدة على المنتج ولا تمثل موقعًا أو متغيرًا.
2. `order_items.inventory_product_id` اختياري، ولا يوجد ارتباط دائم بمتغير أو موقع تخزين ولا snapshot منظم.
3. إضافة بند طلب تقبل الاسم والسعر من العميل ولا تعيد تسعير البند من قاعدة البيانات.
4. انتقال حالة الطلب لا ينشئ حجزًا ولا حركة مخزون.
5. تعديل الكمية الحالي read-modify-write وغير مقفول، ويمكن أن يفقد تحديثات متزامنة.
6. لا توجد جداول لمواقع التخزين أو مستويات المخزون أو الحركات أو الحجوزات.
7. رفع مرجع/إثبات دفع ينشئ دفعة Pending، لكن لا توجد استرجاعات مستقلة أو إجمالي صافي بعد الاسترجاع.
8. دورة الطلب الحالية قصيرة (`new → confirmed → processing → ready → delivered`) ولا تمثل الشحن أو التبادل.

## خطة الاستبدال التدريجي

- إبقاء جداول `inventory_products`, `orders`, `order_items`, `payments` وأعمدتها القديمة للتوافق.
- إضافة متغير افتراضي وموقع افتراضي لكل بيانات قديمة، ثم نقل الرصيد إلى `inventory_stock_levels`.
- اعتبار `quantity_available` حقل توافق قديم فقط، وعدم الكتابة إليه من الواجهات الجديدة.
- تركيب Routes التجارة المحسنة قبل Routes القديمة على المسارات نفسها؛ وبذلك تستبدل العمليات الحساسة دون إنشاء تطبيق أو نظام ثانٍ.
- تنفيذ الحجز والاستهلاك والتحرير داخل PostgreSQL transaction مع `SELECT ... FOR UPDATE`.
- استخدام snapshot في بند الطلب للتاريخ، مع بقاء FK حقيقي للمنتج والمتغير والموقع.
- حساب الأسعار والإجماليات وحالة الدفع على الخادم فقط.

## حدود التوافق

- البنود اليدوية القديمة تبقى قابلة للقراءة، لكن البنود الجديدة المرتبطة بالمخزون يجب أن تختار متغيرًا وموقعًا.
- أسماء الحالات القديمة تُرحّل إلى الحالات الجديدة دون حذف الطلبات.
- rollback يحذف البنية الجديدة فقط بعد إعادة القيمة التجميعية إلى `quantity_available`، ولا يحذف الطلبات أو المنتجات القديمة.
